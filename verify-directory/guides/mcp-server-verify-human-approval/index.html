MCP human approval: what a server can verify, and what it can't

Picture two calls to the same MCP (Model Context Protocol) tool. In the first, the agent lays out who will receive an email, by when, and what it asks for; the user reads it, spots nothing wrong, and clicks Allow. In the second, the model skips all of that and calls the tool straight away. Seen from the server, the two calls are identical: same tool name, same arguments, same credential.

That is the position of anyone who builds an MCP tool with a consequence. The human-in-the-loop confirmation you designed happens in the client, and none of it reaches you. I build DokuTrak, a client document collection tool built for accountants, lawyers and other professionals, and our open-source connector has one tool that emails a real person. This article sorts what our server can guarantee about that tool, whatever the agent says, from what it cannot know at all. Then it asks what a verifier standing outside, such as Horizon Shield's MCP Verification Gate, could check.

Key Takeaways

  • The human's yes for an MCP tool is given in the client. No part of it travels to the server, so the server can't tell an approved call from an unapproved one.
  • What a server can guarantee is what it enforces on every call regardless of consent: acts only a signed-in person may take, an allow-list for agent keys, a recipient fixed when the request is created, revocation on the next call, and an audit trail that also keeps refusals.
  • An outside verifier can compare what a server declares with how it behaves, and replay refusals. It can't see the yes either.

Where human approval actually happens

Human approval for an MCP tool call happens entirely in the client. Our open-source connector, dokutrak-mcp (version 0.1.1), exposes four tools. Two only read. A third flags rejected files and puts the request back on its reminder schedule, without emailing anyone. The fourth, create_request, builds a request for documents and emails it to the client in a single call, and that email can't be taken back. Every layer that makes a person confirm it is client-side.

  • The description. It tells the model to lay out the recipient, the deadline, every document in the words the client will see, and any message, then to call "only once they have confirmed, even when the request already looks complete." Whether the model obeys is up to the model: in one of our tests, on September 15, 2026, it called the tool without showing the recap.
  • The annotations. The tool declares destructiveHint: true, idempotentHint: false and openWorldHint: true, and its _meta carries anthropic/requiresUserInteraction, a key defined by Anthropic rather than by the spec. As of September 2026, Claude Desktop asks before running a tool flagged destructive, and Claude Code asks on every call to a tool carrying that key, auto mode included.
  • The prompt. The client draws it, the user answers it, and the client acts on the answer.

The MCP specification for tools agrees: annotations are hints a client should rely on only when it trusts the server, and keeping a person able to refuse a call is a recommendation addressed to applications, not to servers. The server gets the request afterward, with no trace of what came before it.

What the server actually receives

Our MCP server is a thin local process. It turns a tool call into HTTP requests against our API, authenticated with a key the professional created for their agent, and every check below lives in that API; that is what I mean by "the server" from here on. Here is all it learns about the caller, trimmed from the middleware that reads the key:

req.auth = {
  userId: context.userId,
  organizationId: context.organizationId,
  apiKeyId: context.apiKeyId,
  // 'mcp' when the key was minted for an Agent Connection
  actorChannel: context.origin === 'mcp' ? 'mcp' : 'api_key',
};

Key, workspace, channel. There is no field for "a person approved this," because nothing could fill it honestly. Even mcp is narrower than it sounds: it says the key was issued for an agent, not that the call came through MCP, and not that anyone looked at it.

It is tempting to add the missing field yourself, say a confirmed: true argument. It would prove nothing: the model that might skip the recap is the one that would write true. A confirmation becomes a statement the agent makes about itself.

What an MCP server can enforce without seeing consent

A server that can't see consent can still enforce rules that don't depend on it. Ours enforces five.

Acts only a signed-in person may take. Approving or rejecting a document, including approving all of a request's files at once, is refused unless the call comes from a browser session. The check allows one channel, session, rather than blocking a list of machine channels, so anything else is refused, including a key the professional created for their own scripts, whatever role that key carries.

Such a user key gets a 403 of type approval-requires-human. An agent key doesn't even reach that check: the allow-list below refuses it first, with its own error type. Two independent checks, and a test asserts which one fires first.

An allow-list, not a deny-list. An agent key reaches only an explicit list of endpoints, each entry naming the agent tool that needs it. We rejected a deny-list because it would have left POST /v1/api-keys open: an agent could mint itself an unconfined key in one call. Anything off the list answers 403 agent-endpoint-not-allowed.

No address at send time. The send step takes no recipient. It goes to the address stored on the request when it was created.

Revocation on the next call. The key is looked up in the database on every request, and nothing about it is cached. A revoked key gets the same 401 as a key that never existed.

A record that keeps refusals. The approval and allow-list refusals write an auth.failure row, with the caller's channel, before the response leaves; a revoked key's attempt is logged too. A Postgres trigger rejects any UPDATE or DELETE on the audit table. That protects the table, not the database: a role allowed to drop the trigger could still rewrite history, and our threat model says so.

The connector is open source; the API isn't, so these five points are my description, not something you can read in the repo. The refusals are what anyone holding a key can confirm.

What an MCP server can't prove about a tool call

Of the five claims below about a call to create_request, our server establishes one.

Claim Established by our server? Why
An agent key did not approve a document Yes Refused on every call and logged
A person read the recap and said yes No The recap and the prompt stay in the client
The client honored the annotations No The client reads them; the call carries no record of whether a prompt was shown
The recipient is the right person No recipient_email is what the agent wrote; the server checks the format, then binds it
A session means a human at the keyboard No The server checks the channel, not who is using it

The recipient row is the one I think about most. The server sends only to the stored address, but it can't tell a correct address from a wrong one that exists. Only the recap puts that address before the professional's eyes, which is why we keep it even though the client already asks before the call runs.

What an outside verifier could test

Horizon Shield's gate measures MCP servers from outside and publishes each verdict with a hash anyone can recompute. Its method page explains why it won't execute tools unless the owner asks: "the first tool a server lists may well be destructive." Its verification spec has each verdict list what it establishes and what it does not, the split this article has been drawing.

Here is what I think a verifier of that kind could check on a tool like ours. These are proposals; we haven't run any of them. Our connector also speaks stdio on the user's machine, so today it wouldn't meet the gate's first condition: an endpoint reachable from the public internet.

Declared surface over time. From tools/list alone, a verifier can record that the tool which emails someone declares destructiveHint: true and carries the confirmation _meta key, while the two tools that only read declare readOnlyHint: true. The gate keeps a hash per tool over the name, the description and the input schema and, since version 0.4.19, a second hash over the annotations, _meta, output schema and title. That second hash was added after an early draft of this article pointed out the gap. A release that quietly dropped destructiveHint would show up as a dated change. The gate records that the hint moved; it does not judge whether the new value is true.

Which tools a verifier may run. Annotations are self-declared, so they can't prove a tool is harmless. They can still give a verifier a floor: never execute a tool its own server calls destructive, even with consent.

Refusals, replayed. With consent and a sandbox workspace, the calls built to fail are the safest ones to make. They should change nothing but the audit log and answer identically each time: an agent key on an approval route gets 403 agent-endpoint-not-allowed, a user key gets 403 approval-requires-human, a revoked key gets 401. Those refusals live in our API, one layer under the connector, which exposes no approving tool at all. An MCP-only gate wouldn't reach them; it would need an agent key and direct HTTPS access to the API.

What stays out of reach. The yes itself. A verifier outside the client sees no more of it than we do.

Four habits for MCP builders

  1. Write down what your server knows about a caller. If "a human approved" isn't one of the fields, don't let your docs imply it is.
  2. Guard human-only acts by channel, not by tool list. Leaving a tool out of your MCP server hides it from the model; the endpoint is still there for any key.
  3. Make refusals typed, repeatable and logged. They are the part of your design a stranger can replay.
  4. Publish what you don't establish, with the same prominence as what you do.

FAQ

Can an MCP server verify human approval of a tool call?

Not from the protocol. The permission prompt and any recap happen in the client, and the call that reaches the server carries no proof of either. A server can only enforce rules that hold whether or not someone approved.

Are MCP tool annotations like destructiveHint enforced?

No. They are hints that a client may act on. As of September 2026, Claude Desktop shows a prompt for any tool marked destructiveHint: true, and Claude Code prompts whenever anthropic/requiresUserInteraction is set. A client that ignores them loses that layer, and the server isn't told.

What should an MCP server enforce itself?

Anything that must hold even if the agent is wrong: decisions reserved to a signed-in person, the endpoints an agent key can reach, a recipient fixed at creation rather than at send time, immediate revocation, and a log that records refused attempts along with successful ones.

Can an MCP server check that an email goes to the right person?

No. It can bind the send to the address stored when the request was created, but it can't tell a correct address from a wrong one that exists. Only a recap shown to a person before sending catches that.
